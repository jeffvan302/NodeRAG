# NodeRag Managed Chat Context, Archives, and Reconciliation

**Applies to:** Chat stage C10 in the WSL2/Linux Docker testbed
**Migration head:** `000028_chat_managed_context`
**Feature flags:** `chat.context.enabled`, `chat.ui.enabled`, and `chat.import.enabled`
**DSM package:** intentionally deferred to C11

## Provider boundary

Ollama in Chat always means **Ollama Cloud**. NodeRag does not install, discover, or call a local,
self-hosted, forwarded, or custom Ollama server for Chat. Ollama Cloud generation uses the fixed
hosted `/api/chat` API. Chat internet research uses Ollama Cloud's hosted `/api/web_search` and
`/api/web_fetch` APIs, even when OpenAI OAuth is the response model. Context compression may select
Ollama Cloud or OpenAI OAuth as its L2/L3 model, but it never gains an internet tool.

## What managed context does

Managed context keeps a long chat inside a verified model capacity without deleting its original
history. Before every provider request, and again after every tool result, NodeRag conservatively
estimates the request and enforces the saved capacity and reserves.

The active request is assembled from four layers:

1. **L1 exact pins:** committed messages a user deliberately pins. These remain verbatim and are
   limited by the configured pin budget.
2. **L2 narrative:** a bounded, fallible summary generated by the configured compression model.
3. **L3 structured state:** strict JSON holding goals, constraints, preferences, decisions, failed
   approaches, questions, entities, phase, and flagged notes.
4. **L4 recent history:** complete user/assistant turns kept exactly. An unfinished turn is not
   treated as complete.

Provider-reported usage is stored when available. Before that report exists, the conservative
NodeRag estimator is labelled as an estimate. An unknown model context size fails closed for managed
mode; signing in or listing a model is not described as measuring its context window.

## Using managed context

1. In **Administration → Context window**, save verified capacities for the response and L2/L3
   models, configure the reserves and layers, and pass the synthetic preview.
2. In **Administration → Chat settings**, select managed context as the default only after it is
   reported ready.
3. Create a Chat using **Managed context**.
4. Use **Pin** on a committed message to keep it exactly. Use **Pinned** to remove the pin; the
   original message remains in history either way.
5. The context status shows active, folded, and pinned message counts plus the last snapshot/job.
6. Use **Preview compression** for a read-only dry run. It shows which complete turns would fold,
   recent turns retained, exact pins, estimated source tokens, and whether L2/L3 run sequentially or
   concurrently.
7. Select **Compress context** only after reviewing the preview. A queued or running job exposes
   **Cancel compression**.
8. Use **View older logs** to page earlier messages. Folded messages are labelled **Archived from
   context** and are read only after their referenced sealed segment passes integrity verification.

Automatic compression runs when a managed request reaches its saved trigger or has eligible older
complete turns. L2 and L3 run concurrently only when the administrator permits at least two parallel
runs and the layers use distinct providers; otherwise they run sequentially. A timeout, cancellation,
or expired lease is durable. An expired job can be reclaimed once, while a cancelled job is terminal.

## Compression and archive safety

Messages are never deleted by compression. NodeRag first validates the proposed L2/L3 layers and the
resulting request budget. Only then does one database transaction:

- insert an immutable context snapshot and layer hashes;
- mark the selected original rows as folded;
- link the snapshot and folded rows to the corresponding log segment;
- record the durable job result and hash-chained event.

If a new L2 or L3 layer fails and a prior valid layer exists, that prior layer is retained and the
receipt records the fallback. If no prior valid layer exists, the job fails and folds nothing.

Chat events are written as canonical, newline-terminated NDJSON with event and segment hash chains.
Sealing writes a deterministic gzip file, synchronizes it, verifies its compressed and uncompressed
hashes, updates an immutable archive manifest, and only then retires the active segment. Empty active
segments are valid. Partial final lines, reordered events, bad hashes, unsafe paths, and symlinks fail
closed.

## Existing-folder recovery

**Administration → Chat settings → Recover chats already in this folder** is the only supported way
to adopt an existing `.noderag-chat` tree.

1. Select **Inspect existing chats**. Inspection is read only and never imports or repairs data.
2. Review every candidate, its counts, and its action.
3. Map each source owner to exactly one current local account. A unique matching label is only a
   suggestion; the submitted mapping is explicit.
4. Resolve every quarantine item before enabling **Reconcile eligible chats**.
5. Recheck if the folder changes. Reconciliation binds to the inspected inventory hash, is durable,
   and is idempotent if the same request is retried.
6. Review the operation result. Imported chats start with all tools disabled. The preserved source
   configuration remains recorded as provenance, not as authority to regain permissions.

Portable manifests are content-addressed and written after completed Chat processing. Each includes
the conversation, owner identity, immutable configuration snapshot, messages, runs, and referenced
event segments. Import preserves conversation/event identities only when they do not collide with
local records. Interrupted source runs become safely failed and do not resume external provider work.

Quarantine categories are:

- partial segment;
- checksum mismatch;
- unmapped or conflicting owner;
- future schema;
- duplicate content or identifier collision;
- unsafe path or symlink.

NodeRag does not guess, silently repair, overwrite, merge, or delete quarantined content. Artifact
files remain governed by their own contained storage and full-backup contract; C11 verifies the
combined database, artifact, archive, and credential restore matrix.

## Troubleshooting

- **Context capacity unknown:** save documented capacity for the exact provider/model or use rolling
  context.
- **Pin limit exceeded:** remove an exact pin or increase the independently reviewed L1 limit.
- **Request/tool result too large:** reduce attachments/tool scope, increase a verified context
  capacity, or start a new chat. NodeRag will not send an over-budget continuation.
- **Compression layer failed:** check provider generation health and the saved L2/L3 model. A valid
  previous layer remains active when available.
- **Compression timeout:** inspect the job, verify provider responsiveness, then queue a new dry run.
- **Older logs fail to open:** do not replace the archive. Inspect the recorded checksum/path failure
  and restore from a verified backup.
- **Owner unmapped:** select a local account explicitly, then re-inspect.
- **Checksum/future-schema quarantine:** preserve the source unchanged and restore/export with a
  compatible, verified NodeRag version.

## C10 verification result

The F-drive Docker testbed passed 51 unit files/224 tests, 19 PostgreSQL integration files/118 tests,
and 29 browser tests. The matrix includes long-context arithmetic, exact pins, malformed and failed
layers, retained prior state, timeouts, cancellation, expired-lease recovery, no message deletion,
deterministic archive verification, paged older logs, clean/repeated import, owner conflicts, partial
segments, bad checksums, and future schemas. Migration, OpenAPI, authorization, type-check, lint,
format, boundaries, build/smoke, licenses, SBOM, and secret scanning also pass. Real DSM execution
remains a C11 acceptance activity.
