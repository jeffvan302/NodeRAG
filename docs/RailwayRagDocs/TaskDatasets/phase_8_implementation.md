# Task Dataset Phase 8 Implementation

## Outcome

Phase 8 turns the Task Dataset fast path into an operable large-data subsystem.
Reports can summarize or export large compiled datasets without replaying every
record through model context. Storage growth is bounded by quotas, repeated
query patterns—not model guesses—drive optional indexes, deletion is visible
and resumable, and operators can inspect health before a scale issue becomes a
failed Task run.

The migration head is:

```text
20260826000400_task_dataset_phase_eight
```

This phase preserves every earlier ownership boundary:

- the group remains tenant + saved Task + silo + explicit project-or-no-project;
- every step in the same saved Task run shares one active-plus-staged view;
- no Task can read another Task's datasets;
- stable document IDs still control RAG exclusion coverage;
- failed Task runs still publish none of their staged dataset work; and
- raw source-derived data is untrusted data, never executable instruction.

## 1. Bounded Aggregate Reads

### 1.1 Why aggregates exist

Paging one million JSON records into a model merely to count by region or total
a budget defeats the reuse objective. Phase 8 adds a server-side aggregate path
for the common reporting operations:

- `count`;
- `sum`;
- `avg`;
- `min`; and
- `max`.

An aggregate accepts at most three grouping paths, eight uniquely named
measures, twelve exact filters, and 500 returned groups. Its serialized response
may not exceed 512 KiB. `count` needs no record path; the other operations
require a schema field whose declared type includes `number`.

### 1.2 Definition authorization

`searchPolicy.aggregatePaths` is the allowlist. A path used for grouping or a
numeric measure must be declared there. A filter path must be declared both
filterable and aggregate-capable. The web/runtime checks the definition and the
bounded JSON Schema before calling the database. The database independently
validates pointer syntax, operation names, aliases, array bounds, and limits.

Definitions saved before Phase 8 have no `aggregatePaths` member. For those
legacy definitions only, the declared filterable and sortable paths form the
compatibility allowlist; once `aggregatePaths` is explicitly present—even when
empty—it is authoritative. This permits existing Task caches to gain bounded
summaries without silently widening a newly authored definition.

This separation prevents a model from turning an aggregate into an arbitrary
JSON expression or SQL fragment.

### 1.3 Current-run semantics

The model tool can aggregate the current Task run before commit. The database
builds a visible overlay:

1. select staged records owned by the current run transaction;
2. select the active generation;
3. hide an active record when staged data contains the same dedupe identity;
4. apply exact filters and optional conflict state;
5. group and calculate measures.

Consequently, step two can summarize records prepared in step one without
publishing partial work. Outside the verified run, the public API sees only the
active committed generation.

### 1.4 Model guidance

The `task_dataset` model tool includes an `aggregate` operation. The Task prompt
explicitly directs the model to prefer aggregates when the requested answer is
a count, total, average, minimum, maximum, or grouped summary. The result is
marked as source-derived untrusted data and reports:

- matched records across every group;
- total groups;
- returned groups;
- truncation;
- generation; and
- response bytes.

## 2. Measured Expression Indexes

### 2.1 Measurement, not prediction

Every filter, aggregate grouping path, and aggregate measure path is recorded in
`task_dataset_query_path_stats`. Statistics are keyed by dataset, JSON pointer,
and use kind. They retain use count, cumulative duration, and last-use time. The
use-kind contract reserves `sort` so a future declared JSON-path sort can enter
the same measured pipeline; the current stable record pagination sorts only by
`record_seq` and therefore does not fabricate a JSON-path measurement.

The default policy requires five uses before a path becomes an index candidate.
At most four expression indexes may be active/queued per dataset. Both values
are installation-configurable.

### 2.2 Queue and maintenance ownership

Meeting the threshold inserts one idempotent
`task_dataset_expression_index_jobs` row. Task execution never runs DDL. The
maintenance scheduler claims a bounded number of jobs and executes
`CREATE INDEX CONCURRENTLY IF NOT EXISTS` outside an explicit transaction.

The generated index is fenced to:

```text
dataset_id = <measured dataset>
state = active
is_deleted = false
```

Names are generated by the database from the dataset ID and path digest. The
maintenance service accepts only the generated name grammar, UUID dataset IDs,
and valid JSON pointers; it also SQL-quotes pointer literals. A failed
concurrent build can leave an invalid Postgres index shell, so maintenance
drops that invalid shell before retrying and treats an already-valid index as a
completed idempotent operation. Failed jobs keep a bounded error and may retry
three times.

Index creation and Dataset deletion share a per-dataset lifecycle lock. Purge
drops each measured physical index before deleting its definition, including an
index that finished while deletion was waiting. This prevents empty orphaned
partial indexes from accumulating after Task, group, or dataset clears.

### 2.3 Operational interpretation

An index job is evidence that a path is repeatedly queried, not a promise that
Postgres will use it for every operator. Text equality/grouping gains the most.
Numeric range/aggregate casts may still favor sequential scans depending on
selectivity. The dashboard therefore shows both measurements and job state;
operators can correlate real latency with the installed index before changing
policy.

## 3. Quotas and Parallel Safety

### 3.1 Effective defaults

`task_dataset_quota_policies` stores one optional policy per tenant. In the
absence of a row, effective defaults are:

| Limit                          |   Default |
| ------------------------------ | --------: |
| Definitions per group          |        48 |
| Definition warning threshold   |        12 |
| Active records per group       | 1,000,000 |
| Active bytes per group         |     1 GiB |
| Active records per Task        | 4,000,000 |
| Active bytes per Task          |     4 GiB |
| Source snapshots per group     | 1,000,000 |
| Staged write bytes per run     |   256 MiB |
| Expression indexes per dataset |         4 |
| Uses before index candidate    |         5 |

The internal quota endpoint reads effective values and applies validated partial
updates. Limits are deliberately large enough for real report datasets while
still stopping runaway schema creation, duplicated extraction, or an accidental
unbounded write.

A definition slot represents one reusable dataset schema or information
category, not one source document. Hundreds of documents can contribute source
coverage and records to the same definition without consuming additional
definition slots. For example, a 20-document source scope processed against 13
template requirements still uses at most 13 definitions; the requirement-by-
document coverage rows and extracted records grow independently inside them.

### 3.2 Enforcement points

- A group row lock serializes definition and source-snapshot admission.
- Recreating an existing dataset key does not consume a second definition slot
  while its staged replacement is waiting to publish.
- A statement-level contribution trigger measures the complete staged payload
  and evidence footprint for each affected run after an insert statement.
- Publication checks the resulting group counters and the owning Task totals.
- An advisory transaction lock derived from `task_id` serializes publication
  across different silo/project groups for the same Task. Two parallel runs
  therefore cannot both observe the other's old total and race over the Task
  quota.

Quota failure aborts the current statement/transaction. It never mutates the
ready generation. A Task can clear/rebuild, narrow extraction, or have an
operator deliberately raise policy before retrying.

## 4. Background Dataset Export

### 4.1 Request and snapshot

Exports are asynchronous because a large dataset must not hold an API request
open. `task_dataset_request_export` records:

- Task, group, and dataset;
- active generation;
- record-sequence watermark;
- JSON Lines or CSV format;
- selected paths;
- exact filters and conflict state; and
- file name.

The generation plus watermark makes the file repeatable even if a newer Task
run commits while the worker is paging. Because records are incremental between
generations, the export page reconstructs each identity's newest retained
revision at or before the captured generation; it does not rely on that older
row still having its original lifecycle state.

### 4.2 Worker behavior

The queue worker claims one export with a lease and pages at most 500 records at
a time. Each page renews the lease. Projection occurs deterministically:

- JSON Lines writes one projected JSON object per line;
- CSV uses the selected JSON pointers as columns and RFC-style quote escaping;
- every export requires at least one explicitly selected or definition-level
  summary path, so an empty policy can never widen into a raw-payload export;
- object/array cells are compact JSON; and
- values missing at a selected pointer become empty CSV cells or JSON null.

The worker accumulates no more than 50 MiB. It uploads to the private
`generated-files` bucket, inserts a normal `generated_files` row with Task
Dataset metadata, and only then completes the export job. If finalization fails,
it removes the database row and storage object before retrying. A deterministic
size-limit failure is terminal; transient claims/storage errors may retry five
times.

### 4.3 Access

Public API callers list export jobs and receive a `generatedFileId` only after
success. Download continues through the existing authenticated generated-file
route. The worker never returns a private bucket URL in the job record.

## 5. Conflict Review

The conflict review RPC returns active conflicted records in stable record
sequence order with a generation-fenced signed cursor. Each row contains the
logical key, summary, revision, source count, first/last-seen dates, and up to
100 preserved conflict variants.

The operator explorer presents the variants side by side. Phase 8 does not add
a “choose winner” mutation. Resolution needs a real workflow decision about
source precedence, effective dates, evidence retention, and what happens on the
next refresh. Until that is known, read-only review is the safe contract and
the model may still reason over both variants during a Task.

## 6. Visible Lifecycle Deletion

### 6.1 Saved Task deletion

`DELETE /api/v1/tasks/{taskId}` now returns `202 Accepted`. One database
transaction:

1. locks and disables the Task;
2. marks it `deleting` with a request timestamp;
3. cancels queued/running Task runs and items;
4. discards open/sealed/failed-commit Dataset transactions;
5. marks every related group and definition deleting;
6. advances every group generation and clears publication leases;
7. creates a deletion operation with pre-delete counts; and
8. creates a resumable Task purge job.

Database write fences also reject new Task items/runs and non-cancellation run
updates once deletion begins. This closes the race between an application-level
“is active” check and the deletion transaction; a late worker cannot publish a
successful run over the cancellation state.

Maintenance removes receipts, contributions, batches, records, usage, sources,
measured indexes, definitions, run transactions, groups, and finally the Task.
Queued or processing exports are cancelled when deletion begins. The operation
is then marked succeeded with deleted counters. It is intentionally not tied by
a foreign key to the Task so status remains available after the Task row is
gone.

If maintenance exhausts its bounded attempt, it marks the operation failed and
the still-present Task `deletion_failed` with the same bounded error. Retrying a
delete while queued/running returns the existing operation rather than creating
duplicate work.

### 6.2 Silo and project deletion

Database `BEFORE DELETE` fences on silos and projects inventory related Task
Dataset groups, discard open transactions, invalidate generations/leases,
cancel competing purge jobs, and record a succeeded deletion operation before
the existing foreign-key cascade removes rows. This keeps deletion correct even
when it originates outside the web route.

## 7. Vacuum, Purge, Bloat, and Partition Decisions

The record and contribution tables use a 2% autovacuum scale factor with lower
fixed thresholds. Source snapshots and record embeddings use 3%. Analyze
thresholds are lower than vacuum thresholds so JSONB/statistical changes reach
the planner promptly. The maintenance purge default increases to 1,000 rows per
bounded batch and retains row-lock/heartbeat resumability.

The operations dashboard reads `pg_stat_user_tables` for the high-churn tables
and reports live rows, dead rows, dead percentage, relation bytes, last
autovacuum/analyze, and cumulative automatic maintenance counts.

Phase 8 does not partition any table. It emits `review_measured_table_sizes`
only when a core records/contributions table reaches either:

- 5,000,000 estimated live rows; or
- 5 GiB total relation size.

Below those thresholds the decision is `not_justified`. Crossing a threshold
starts an operator design review; it does not automatically rewrite production
tables.

## 8. Operator Explorer

The top-level Task Datasets browser retains silo → Task → project/no-project
group → dataset selection and adds:

- bounded summaries with group/measure/filter controls;
- background export creation, status, and generated-file download;
- review-specific dated conflict comparison;
- effective quota and quota-pressure telemetry;
- hot path and expression-index job state;
- export, purge, and deletion operation counters;
- live/dead row and autovacuum health; and
- the measured partition recommendation.

Vectors remain excluded. The view exposes configuration and bounded projections,
not raw embedding columns.

## 9. Public and Internal API Surface

Public additions:

- `POST .../datasets/{datasetId}/aggregate`;
- `GET|POST .../datasets/{datasetId}/exports`;
- richer `GET .../datasets/{datasetId}/conflicts`;
- `GET /api/v1/task-dataset-operations`; and
- `GET /api/v1/tasks/{taskId}/deletion`.

The public operations response is tenant-scoped and omits installation-wide
physical table statistics and the partition recommendation. Those values can
reveal aggregate activity across tenants and therefore remain limited to the
authenticated internal operator explorer. Public callers still receive their
own quota, usage, queue, hot-path, index, export, purge, and deletion state.

Internal control-plane additions mirror aggregate/export/operations and add
`GET|PATCH /api/task-dataset-quotas` for validated installation policy changes.
Export creation and Task deletion return `202` because their physical work is
background-owned.

## 10. Backup and Installation Contract

Quota policies are durable installation data and are included in portable
backup order. Query-path statistics, expression-index jobs, export jobs,
deletion operations, embedding jobs, and purge jobs are operational/rebuildable
state and are excluded from portable archives. Generated export files remain in
the normal generated-files backup bucket policy.

The platform contract requires all five Phase 8 tables and its service-role-only
RPCs. The staging deployment gate applies the Phase 8 migration and runs the
Phase 1 through Phase 8 SQL smoke suites before acceptance.

## 11. Verification and Acceptance

The Phase 8 SQL integration smoke proves:

- new tables and RPCs are service-role-only;
- grouped count/sum returns exact values;
- measured uses queue one idempotent index job;
- a hard definition quota rejects the next write;
- two dated conflict variants remain visible;
- an export captures and completes a fixed three-record snapshot;
- operations return no vectors and no premature partition recommendation;
- autovacuum reloptions are installed; and
- Task deletion remains visible, purges in batches, removes the Task last, and
  retains a succeeded operation.

Type/unit coverage additionally checks aggregate schemas and numeric pointer
typing, CSV/JSON projection and escaping, concurrent-index SQL fencing and
injection guards, scheduler integration, Task API/UI behavior, and existing
Phase 1–7 regression suites.

## 12. Deliberate Deferrals

Phase 8 does not add:

- cross-Task dataset reads or sharing;
- arbitrary model-authored SQL or indexes;
- raw vector export;
- automatic partition creation;
- operator mutation of conflict winners; or
- reopening coverage when a document is re-ingested under the same stable ID.

Those boundaries preserve the original purpose: reuse trusted, Task-private
compiled work while keeping ownership, freshness, publication, and deletion
predictable.
