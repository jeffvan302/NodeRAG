# Document Engine — Purpose, Architecture & Operating Model

**Status:** Architectural overview
**Purpose:** Explain why the Document Engine exists, how the Template Analyzer and Agent Document Write/Render Tool work together, and how they extend the existing agent/RAG workflow from Markdown output to professionally formatted Microsoft Word documents.

First-class ownership, Template Group tools, and catalog search are specified in
[Template Catalog And Template Group Tools](template_catalog_and_group_tool_spec.md).
Per-template storage and deterministic DOCX decomposition are specified in
[Template DOCX Ingestion And Storage](template_docx_ingestion_and_storage_spec.md).

---

## 1. Executive Summary

The Document Engine adds a reusable Microsoft Word output capability to the existing agent system.

Today, the agent can research information through RAG and supporting document tools, reason about the information it finds, and successfully produce Markdown files. The new Document Engine keeps that research and content-generation capability, but adds a way to place the same information into arbitrary Word document templates while preserving the template's original visual design.

The system is intentionally divided into two independent tools:

1. **Template Analyzer / Blueprint Compiler**
   Takes a Word `.docx` template and analyzes its structure, layout, instructions, images, tables, repeating regions, and other document elements. It produces a reusable **Template Blueprint** that explains what the template means and how it may later be populated.

2. **Agent Document Write / Render Tool**
   Takes an approved Template Blueprint, the original Word template, and content gathered or generated by the agent. It validates the supplied data and deterministically renders a new `.docx` document from the original template.

The central design principle is:

> **Analyze the template once, reuse the blueprint many times, and always preserve the original DOCX as the physical source of truth for layout and formatting.**

The model is responsible for understanding meaning and generating content. Deterministic document code is responsible for manipulating the Word package safely.

Templates are not stored inside reference libraries. Every template belongs to
exactly one Template Group, and that group defines one dynamic tool that searches
the titles and detailed-description vectors of renderable templates inside the
group.

---

## 2. The Problem This Solves

The objective is not to build a report generator for one fixed Word template.

Templates may differ substantially from one use case to another. A template may contain:

- explicit placeholders such as `{{municipality_name}}`;
- natural-language instructions such as “Provide a 2–4 sentence executive summary here”;
- blank paragraphs under a heading that imply content should be inserted;
- example rows in a table that actually represent a variable-length collection;
- logos or decorative images;
- replaceable image locations;
- graphs or chart areas;
- colored boxes, shaded tables, shapes, and callouts;
- headers and footers;
- different page orientations;
- repeating pages or blocks;
- optional sections;
- static text that must never be altered.

A conventional mail-merge approach assumes that the template author has already placed well-defined variables into the document. That assumption is too restrictive for this system.

Instead, the Document Engine must be capable of taking a human-designed Word document and determining:

- what is static;
- what is dynamic;
- what each dynamic area is asking for;
- which structures repeat;
- how many rows or blocks may be needed;
- which images should remain unchanged;
- which images may be replaced;
- which formatting and layout must be preserved;
- what instructions the agent must follow when generating the content.

This is why the system first converts each new Word template into a reusable semantic blueprint.

## 3. High-Level Architecture

```text
                    DOCUMENT ENGINE

             ┌─────────────────────────┐
             │   Word DOCX Template    │
             └────────────┬────────────┘
                          │
                          ▼
             ┌─────────────────────────┐
             │    Template Analyzer    │
             │   / Blueprint Compiler  │
             └────────────┬────────────┘
                          │
                          ▼
             ┌─────────────────────────┐
             │   Template Blueprint    │
             │  + Original DOCX Asset  │
             └────────────┬────────────┘
                          │
             reused for many documents
                          │
                          ▼
 User Request ──► Agent / RAG / Source Tools
                          │
                          ▼
             ┌─────────────────────────┐
             │      Agent Data         │
             │  structured + optional  │
             │    Markdown content     │
             └────────────┬────────────┘
                          │
                          ▼
             ┌─────────────────────────┐
             │ Agent Document Write /  │
             │      Render Tool        │
             └────────────┬────────────┘
                          │
                          ▼
                    Final DOCX
                          │
                          ├──► Generated Files storage
                          │
                          └──► Optional PDF / visual QA
```

The system therefore has two very different phases:

### Template preparation phase

Performed once whenever a new template, or a new version of a template, is introduced.

### Document generation phase

Performed whenever an agent needs to create a document from that template.

The expensive semantic interpretation of the Word template does **not** need to be repeated for every generated report.

### Template catalog and discovery

The Document Engine is supported by a first-class template catalog:

```text
Template Group (one model tool)
    └── Templates (one required group each)
            ├── title search
            ├── detailed-description vector search
            └── active approved version + blueprint
```

The group tool performs title, semantic, or hybrid search within its own group.
It returns candidate templates, not RAG evidence and not full blueprints. After
the agent selects a template, `get_template_contract` loads the approved
contract and `write_document` renders it. This avoids injecting every large
template contract into every model run.

OpenAI OAuth-backed reasoning models may assist with template authoring and
semantic analysis after those task keys are explicitly allowed by the runtime.
They do not produce description vectors; a separately configured Template
Catalog embedding model owns that derived data.

Before the Template Analyzer performs semantic work, a dedicated ingestion
stage follows a typed template instruction contract. It preserves the immutable
DOCX, snapshots the Template Configuration, inventories package relationships,
extracts original image bytes into the template's private namespace, records
every image usage, and produces stable physical structure. This stage is not
the ordinary document/RAG ingestion path.

## 4. Tool 1 — Template Analyzer / Blueprint Compiler

### 4.1 Purpose

The Template Analyzer turns an arbitrary Word document into an internally understood, reusable template.

It does not generate the final report.

Its purpose is to answer:

> “What is this document, what parts of it can or should change, what do those parts mean, and exactly where are they located in the Word package?”

The output is a **Template Blueprint**.

---

### 4.2 What the Analyzer Receives

The primary input is:

```text
template.docx
```

The Analyzer may additionally receive:

- a template title;
- template version metadata;
- tenant/project ownership;
- optional author notes;
- optional user instructions about the intended purpose of the template.

The Analyzer must not assume that the document follows any particular placeholder convention.

---

### 4.3 What the Analyzer Does

The Analyzer has two complementary responsibilities.

#### Deterministic DOCX inspection

Application code opens the DOCX package and determines its exact physical structure.

This includes:

- document sections;
- paragraphs and text runs;
- tables, rows, and cells;
- merged cells;
- paragraph and table styles;
- section breaks;
- portrait/landscape orientation;
- margins;
- page breaks;
- headers and footers;
- drawings;
- images;
- relationships;
- image anchors and placement;
- text boxes;
- hyperlinks;
- content controls;
- bookmarks;
- other relevant Open XML parts.

This deterministic pass produces stable element addresses and extracts assets such as embedded images.

#### Model-based semantic interpretation

A capable multimodal model is then given the complete logical DOCX package:
the package and asset manifests, relationship graph, readable OOXML parts, and
content controls. Dedicated read tools let it revisit exact parts and inspect
original image assets; dedicated write tools capture structure, content,
layout, and asset mappings without granting write access to the DOCX package.

The model determines intent, such as:

- this paragraph is an instruction;
- this blank area is intended for an executive summary;
- these sample rows represent one repeating collection;
- this image is static branding;
- this image appears to be a replaceable logo;
- this shaded area is a KPI block;
- this section is optional;
- this page is a repeating initiative-detail page;
- these columns correspond to specific semantic fields.

The division of labor is deliberate:

> **Code understands exact Word structure. The model understands human intent.**

The model should never be expected to safely edit raw Word XML.

## 5. The Template Blueprint

The blueprint is not a replacement for the Word document.

The original DOCX remains stored and immutable as the physical source of truth for:

- formatting;
- positioning;
- styles;
- colors;
- borders;
- page geometry;
- headers and footers;
- drawing anchors;
- shapes;
- branding;
- theme information.

The blueprint acts as a **semantic map and mutation plan**.

It tells later document-generation code:

- what a dynamic region means;
- where it is located;
- what type of content belongs there;
- what operation is permitted there;
- what instructions the agent must follow;
- what should be preserved;
- whether the item is required, optional, or repeating.

A simplified conceptual example:

```json
{
  "templateId": "uuid",
  "templateVersion": 1,
  "bindings": [
    {
      "fieldId": "executive_summary",
      "type": "rich_text",
      "operation": "replace_content",
      "instruction": "Provide a concise 2–4 sentence executive summary.",
      "target": "internal-element-address"
    }
  ],
  "collections": [
    {
      "collectionId": "priority_initiatives",
      "operation": "repeat_table_row",
      "prototypeRow": "internal-row-address",
      "fields": [
        "initiative",
        "owner",
        "execution_status",
        "milestone",
        "funding_gap",
        "leadership_note"
      ]
    }
  ],
  "assets": [
    {
      "assetId": "municipality_logo",
      "operation": "replace_image",
      "preservePlacement": true
    }
  ]
}
```

The exact internal element addresses remain server-side and do not need to be exposed to the agent.

## 6. Images and Layout

Layout is a first-class part of the system.

If a Word template contains an image positioned against the left side of a page, the Analyzer should understand both:

1. the image asset itself; and
2. the drawing/positioning information that places it there.

Embedded images can be extracted from the DOCX package and cataloged as template assets.

However, when generating a new document from the same template, the preferred behavior is usually **not** to remove and recreate static images.

Instead:

- copy the original DOCX;
- preserve the original image;
- preserve its drawing anchor;
- preserve its wrapping behavior;
- preserve its size and positioning.

If the blueprint identifies the image as replaceable, the renderer may replace the underlying image while retaining the existing layout metadata.

This same preserve-first principle applies to:

- page decorations;
- logos;
- shapes;
- shaded blocks;
- headers;
- footers;
- table styling;
- page orientation;
- margins;
- section structure.

The Document Engine should modify only areas explicitly authorized by the blueprint.

---

## 7. Why the Analyzer Is a Separate Tool

The Analyzer should be separate because template understanding and report generation are different jobs.

A new template may require substantial analysis:

- parsing Open XML;
- extracting images;
- rendering pages;
- vision analysis;
- semantic reasoning;
- confidence scoring;
- optional human review.

That cost should be paid once.

After approval:

```text
Template v1
    │
    ▼
Analyze once
    │
    ▼
Blueprint v1
    │
    ├── Report 1
    ├── Report 2
    ├── Report 3
    ├── Report 4
    └── Report 500
```

If the template changes, it becomes a new version and is analyzed again.

This creates a reliable and versioned internal template catalog that can be prepared in advance before an agent ever needs to generate a document.

---

## 8. Tool 2 — Agent Document Write / Render Tool

### 8.1 Purpose

The second tool is used during a normal agent run.

Its job is to combine:

- the approved Word template;
- the approved Template Blueprint;
- information gathered by the agent through RAG and source tools;
- structured Agent Data;
- optional Markdown content;
- supplied images or generated chart images;

and render a valid final `.docx`.

A recommended tool name is:

```text
write_document
```

This should be a true tool execution, not merely a signal that the agent has finished its answer.

---

## 9. The Agent's Role

The agent remains responsible for research and content.

The agent:

1. receives the user's request;
2. receives the semantic contract derived from the blueprint;
3. uses the existing RAG search and document tools;
4. finds supporting source information;
5. reasons about what belongs in each template field;
6. writes narrative content where required;
7. builds collection rows where required;
8. supplies assets or chart data where required;
9. produces structured **Agent Data**;
10. calls `write_document`.

The agent does **not** need to know:

- ZIP package layout;
- XML namespaces;
- relationship IDs;
- `word/document.xml`;
- image relationship mechanics;
- drawing anchors;
- how Word represents a table row.

Those details belong entirely to the deterministic renderer.

---

## 10. Agent Data

Agent Data is the interface between agent reasoning and document rendering.

A typical payload may contain:

```json
{
  "fields": {
    "municipality_name": "Example Town",
    "executive_summary": "..."
  },
  "collections": {
    "priority_initiatives": [
      {
        "initiative": "Main Street Improvements",
        "owner": "Public Works",
        "execution_status": "WATCH",
        "milestone": "Bid award — September 2026",
        "funding_gap": 125000,
        "leadership_note": "Confirm grant match source."
      }
    ]
  },
  "assets": {
    "municipality_logo": {
      "fileId": "uuid"
    }
  },
  "charts": {
    "funding_summary": {
      "chartType": "bar",
      "data": {
        "labels": ["Required", "Secured", "Gap"],
        "values": [2500000, 1800000, 700000]
      }
    }
  }
}
```

The blueprint defines the expected schema.

The renderer validates Agent Data before touching the Word document.

## 11. Relationship to the Existing Markdown Workflow

The existing Markdown workflow remains valuable and should not be removed.

The agent already knows how to:

- search RAG;
- gather source information;
- synthesize content;
- produce clear Markdown.

The new system adds a structured document-output stage.

Two operating modes should be supported.

### Preferred mode — structured Agent Data

The agent uses its existing research process but returns data matching the blueprint's semantic schema.

This is the best option for:

- tables;
- repeated rows;
- repeated sections;
- images;
- charts;
- conditional blocks;
- dates;
- currency;
- status fields.

### Compatibility mode — Markdown-to-template mapping

For simpler templates, or to preserve an existing workflow, the agent may continue generating Markdown.

The Markdown can then be:

- inserted into a rich-text template region;
- split into semantic sections;
- mapped into blueprint fields;
- converted into Word paragraphs, headings, lists, and tables where the blueprint permits.

Markdown therefore remains an excellent content representation, but it should not be the only representation because complex Word templates often require structured collections and assets.

## 12. What `write_document` Does

Once called, the render tool should:

1. load the approved blueprint;
2. load the exact immutable template version referenced by the blueprint;
3. verify the template hash/version;
4. validate Agent Data against the blueprint;
5. create a working copy of the original DOCX package;
6. perform only blueprint-authorized mutations;
7. replace text/rich-text fields;
8. repeat or remove table rows as necessary;
9. repeat or remove document blocks as necessary;
10. insert or replace images;
11. generate and insert chart images where configured;
12. preserve unrelated document content and layout;
13. verify that required bindings were satisfied;
14. check for unresolved placeholders or instructions;
15. validate the generated DOCX package;
16. save the final DOCX bytes to generated-file storage;
17. create/update the corresponding generated-file database record;
18. return a persistent file ID and generation result to the agent.

The tool result should indicate actual success or failure.

The agent run should not be considered complete until the requested document has actually been persisted.

---

## 13. Dynamic Tables and Repeating Blocks

One major purpose of the blueprint is to distinguish **sample layout** from **actual record count**.

A template may visually contain six example rows.

That does not mean the generated document must contain six rows.

If the blueprint defines the body row as a repeating prototype:

```text
Template:
  Header
  Prototype row
  Prototype row
  Prototype row
  Prototype row
```

and the Agent Data contains two records:

```text
Generated document:
  Header
  Record 1
  Record 2
```

If Agent Data contains twenty records, the renderer creates twenty rows.

The renderer clones the prototype row so the original Word formatting is retained.

The same concept can be used for:

- initiative detail blocks;
- departmental sections;
- evidence records;
- calendar entries;
- source registers;
- image galleries;
- appendices.

---

## 14. DOCX Generation Does Not Require LibreOffice

The core Document Engine must generate DOCX directly.

LibreOffice is **not** required for:

- opening the template package;
- modifying Word Open XML;
- replacing text;
- repeating table rows;
- inserting images;
- preserving formatting;
- writing the resulting DOCX ZIP package.

The output is a valid `.docx` that can be opened in Microsoft Word.

LibreOffice may later be used as an optional secondary service for:

- DOCX-to-PDF conversion;
- visual rendering;
- pagination inspection;
- page-image generation;
- visual QA.

If LibreOffice is unavailable, DOCX generation should still succeed.

---

## 15. Optional Visual QA

A useful later-stage capability is to render the completed document and allow a vision model to inspect the result.

The vision QA stage can look for:

- unresolved placeholders;
- instructional text that should have been removed;
- clipped text;
- badly split tables;
- unexpected blank pages;
- misaligned images;
- broken chart placement;
- severe layout changes;
- obviously missing content.

This should be treated as a quality-control step, not as the mechanism that creates the DOCX.

---

## 16. Relationship to Existing Generated-File Storage

The existing generated-file storage and provenance model should remain the persistence layer.

The new document capability extends that layer to support binary artifacts such as:

- `.docx`;
- optionally `.pdf`.

The underlying storage implementation therefore needs to support binary bytes/streams in addition to UTF-8 text.

The `write_document` tool should return a persistent generated-file result such as:

```json
{
  "success": true,
  "fileId": "uuid",
  "fileName": "Town-Manager-Report.docx",
  "templateGroupId": "uuid",
  "templateToolName": "municipal_reports",
  "templateId": "uuid",
  "templateVersion": 1,
  "blueprintId": "uuid",
  "warnings": []
}
```

Relevant generation metadata should retain:

- Template Group ID and tool-name snapshot used for discovery;
- template ID;
- template version;
- Template Configuration ID/SHA and ingestion-manifest SHA;
- blueprint ID/version;
- template hash;
- source/provenance information;
- model/provider used;
- generation timestamp;
- validation results;
- unresolved-binding count;
- optional visual-QA results.

This allows a generated report to be reproduced and audited later.

---

## 17. Why Two Tools Instead of One

Keeping the two functions separate provides several advantages.

### Reliability

Template interpretation happens once and can be reviewed before production use.

### Performance

The expensive vision/reasoning analysis is not repeated for every report.

### Predictability

The renderer operates from an approved blueprint instead of asking a model to rediscover the layout during every generation.

### Safety

The model is not given direct control over arbitrary Word XML.

### Reusability

One approved template may generate hundreds or thousands of documents.

### Versioning

A revised Word template produces a new blueprint version while older reports remain reproducible.

### Better development boundaries

The Template Analyzer can evolve independently from the rendering engine.

## 19. Practical User Experience

From the user's point of view, the process should eventually be simple.

### Template preparation

An authorized user first selects or creates a Template Group, then supplies the
template title, detailed description, and Word file. A template cannot exist
outside a group.

The system embeds the catalog description, analyzes the document, and stores it
as an internal reusable template. The Templates section shows version,
blueprint, and embedding status separately.

The user does not have to understand:

- Open XML;
- ZIP packages;
- Word relationship files;
- template variables;
- programming syntax.

The document may have been created normally in Microsoft Word.

### Document generation

Later, the user may simply ask:

> “Create the monthly Town Manager report for July using the approved Town Manager template.”

The agent:

- selects the correct Template Group tool;
- searches titles and description vectors inside that group;
- finds the correct renderable template;
- receives its blueprint;
- searches the required RAG/source information;
- builds the required content;
- calls the document tool;
- returns the completed DOCX.

The Word document should retain the original template's visual identity while containing current, source-supported agent-generated information.

## 20. Core Design Rules

The following principles should guide implementation.

### Rule 1 — The original DOCX owns presentation

Do not rebuild professionally designed templates from scratch unless absolutely necessary.

### Rule 2 — The blueprint owns semantic meaning

The blueprint defines which document regions are dynamic and what they mean.

### Rule 3 — The model owns content decisions

The agent and analysis models reason about meaning, instructions, and source-supported content.

### Rule 4 — Deterministic code owns document mutation

Actual Word-package edits should be performed by code, not by free-form model-generated XML.

### Rule 5 — Analyze once, generate many

Template analysis is a compilation step and should not be repeated unnecessarily.

### Rule 6 — Generation must produce a real persisted artifact

A successful `write_document` call means that the final DOCX has actually been written and has a persistent file ID.

### Rule 7 — Preserve current RAG and Markdown strengths

The new Document Engine extends the current content workflow; it does not replace the existing research and Markdown capabilities.

### Rule 8 — LibreOffice is optional

DOCX creation must work independently. PDF conversion and visual QA may use an optional render service later.

### Rule 9 — Template discovery is group-scoped

Every template has exactly one Template Group. The group defines the model tool,
and title/vector ranking may search only templates inside that group. Template
catalog vectors never enter document RAG results.

## 21. Final Architectural Summary

The system can be understood as four layers:

```text
1. TEMPLATE DISCOVERY

   Template Group Tool
     │
     ▼
   Group-scoped title + vector search
     │
     ▼
   Selected Template


2. TEMPLATE UNDERSTANDING

   DOCX
     │
     ▼
   Template Analyzer
     │
     ▼
   Approved Blueprint


3. CONTENT UNDERSTANDING

   User Request
     │
     ▼
   Agent + RAG + Source Tools
     │
     ▼
   Agent Data / Markdown


4. DOCUMENT CREATION

   Original DOCX + Blueprint + Agent Data
     │
     ▼
   write_document
     │
     ▼
   Final DOCX
     │
     ▼
   Generated Files
```

Together, these layers create a general-purpose document system rather than a hard-coded report generator.

The Template Analyzer makes arbitrary Word templates machine-understandable in advance.

The Agent Document Write/Render Tool then allows the existing agent and RAG infrastructure to populate those templates with current source-supported content and produce finished Word documents while preserving the template's original layout and design.

That separation is the key to making the system reliable, reusable, scalable, and suitable for many different Word document templates rather than only one predefined report format.
