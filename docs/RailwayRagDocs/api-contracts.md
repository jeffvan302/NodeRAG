# POC API Contracts

Last reviewed: 2026-08-15.

This file inventories older admin/internal POC routes. It is not the public
Bubble contract. External integrations must use `/api/v1`; the canonical,
complete public reference is [api-usage.md](api-usage.md), whose route coverage
is enforced by `pnpm docs:check`.

For a REST-only document without Bubble installation material, use the
[REST API command reference](api/rest-api-command-reference.md).

The current implementation uploads files into selected silos, stores records, and queues jobs. Provider-backed worker ingestion supports PNG/JPEG vision ingestion plus PDF, DOCX, Excel, Markdown, text, and CSV source documents through canonical Markdown assembly before chunking and embedding. Ask and Extraction use bounded, model-first tool loops: the request reaches the model before RAG, and the model can escalate from scoped chunk search to exact canonical Markdown ranges with `get_document_markdown`. Their independent task configurations store a 1-250 overall tool-request limit, a separate 0-100 RAG-search limit, plus reference location/time-zone settings, and each provider call receives fresh UTC context. When Swarm Configuration enables the current task, the coordinating model can dispatch two or more independent `swarm_task` workers across configured provider/model routes. Route parallel-call limits are enforced, each worker receives a separate shared-workspace cache slot, detailed worker/tool/timing telemetry is retained in the parent run, and only the coordinator can mutate/finalize a DOCX or publish the final output. Ask and Extraction also receive `model_status`; Ask persists its updates in the ordered event stream, while Extraction and Task items retain server-scoped current status without trusting model-supplied run IDs. Ask, standalone Extraction, and Task runs may register an optional webhook. Every validated model-status call then emits a signed `model.status.updated` callback containing the authoritative original question or active Task item request plus the structured status; delivery attempts are audited against the owning run. Public status responses expose webhook registration/signing booleans but never the URL or secret. For requested Ask files, the model must author the exact Markdown, JSON, CSV, or text artifact through `write_file` or a published `cache_file`; ordinary answer text is not wrapped into a file. DOCX output uses assigned template tools when an appropriate template matches and otherwise uses a structured blank-document fallback, with both paths completed through stateful create/inspect/edit/copy-image/finalize tools. Public callers may receive only the final JSON result or an NDJSON event stream; both modes persist the Ask run and ordered event journal so a disconnected client can recover by run ID. Provider-supported reasoning summaries or thinking text are diagnostic events, while tool events reflect the application tools Railway actually executed. Internal tool routes still receive a `siloId` from Railway/API execution context, but the model-facing tool arguments do not include silo IDs. Saved extraction Tasks are global definitions and only become silo-scoped when a Task run is started; each Task item stores a step name, extraction request, output file name, and output type. A Task may be saved with no items; empty Task runs complete without creating generated files. Each non-empty run executes its extraction items one by one and records per-item generated file IDs, extraction run IDs, status, preview, and errors. Cancelling the parent Ask or Extraction Task aborts its provider call and all swarm workers. Task webhooks also receive lifecycle events; delivery failures are audited without changing the run result.

Large PDFs should be handled as a worker pipeline rather than a single vision call: extract native text where available, render pages or embedded images in bounded batches, ask the configured vision model to describe page images/figures, then write a temporary Markdown file that interleaves text with image-description blocks before RAG ingestion. Poppler should handle native text and page rendering; `pdf-lib` is useful when the system needs actual one-page PDF artifacts. Step-six Markdown assembly can remain deterministic or be delegated to the configured PDF assembly model task, which may use `render_pdf_page` for uncertain pages. Chunking now happens after the complete Markdown file is assembled, using configurable max-token and overlap-token settings so concepts can bridge adjacent chunks and pages. Each chunk stores its source start/end character offsets into the assembled Markdown; RAG neighbor context can therefore be reconstructed from the Markdown span without duplicating overlapped chunk text. Once the temporary Markdown file is ingested into the selected silo, later cleanup can remove the temporary generated-file row and storage object.
