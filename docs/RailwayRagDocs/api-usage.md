# RAG Railway Public API Usage Guide

Last reviewed against the implemented `/api/v1` route handlers: 2026-08-15.

This guide is the canonical contract for the current Railway-hosted public API.
It documents all public method/path combinations for creating silos and
projects, ingesting documents, checking ingestion status, searching RAG
content, asking grounded questions, executing extractions, running saved Tasks,
retrieving generated files, and reading API diagnostics.

The implemented route tree currently contains 97 documented method/path
combinations: 95 client-facing operations and 2 internal RunPod worker
exchanges. The Endpoint Reference and the detailed endpoint headings are
checked automatically against the route handlers so additions, removals, or
stale paths fail the documentation validation step.

The current public API prefix is:

```text
/api/v1
```

The current Railway production base URL is:

```text
https://web-production-3bf65.up.railway.app
```

Use the full API base URL:

```text
https://web-production-3bf65.up.railway.app/api/v1
```

For local development, use:

```text
http://127.0.0.1:3000/api/v1
```

## Current Capabilities

The public API currently supports:

- API-key authenticated requests.
- API-key scopes for separating read, ingest, delete, cancel, reprocess, ask, extract, and generated-file access.
- Standard JSON error responses.
- Request IDs on JSON responses.
- Pagination on list endpoints.
- Idempotency keys on state-changing create, upload, update, delete, cancel,
  reprocess, Ask, Extraction, Task, library, and internal callback operations.
- Usage audit logging per API key in `api_usage_logs`.
- API-key-scoped usage-log retrieval for Bubble diagnostics.
- Optional ingestion/reprocess webhook callbacks.
- Silo-scoped document ingestion.
- Document status, chunks, original downloads, and Markdown text downloads.
- Short-lived signed download tickets for originals, canonical Markdown, and generated files.
- RAG search with source document IDs and full source document names.
- Ask calls against selected silo/document RAG content, including a bounded model tool loop.
- NDJSON Ask streaming with reasoning summaries/traces, model output, tool lifecycle events, and a final result event.
- Durable Ask run status and event recovery after a client disconnect.
- Generated Ask output files when the Ask task has the `write_file` tool enabled.
- Synchronous standalone Extraction execution with persisted run, result, and generated-file records.
- Saved extraction Tasks that run multiple extraction outputs sequentially against a selected silo.
- Generated-file listing and download.
- API-key-scoped reference-library creation, ingestion, search, access grants,
  and Ask/Extraction tool bindings.

### Public API And Internal Tools

Client-callable routes use the `/api/v1` prefix. The two RunPod routes listed
in this guide are internal worker exchanges under the same prefix and accept
short-lived job credentials rather than administrator-created API keys. The
Railway admin UI also uses private `/api/...` routes, and the model runtime has
internal tools such as `rag_search`, `rag_documents`, `list_files`,
`get_document_markdown`, `get_document_image`, `render_pdf_page`, and
`write_file`. Those private admin
routes, internal RunPod exchanges, and model-tool arguments must not be called
directly from Bubble or another external client.

When an external client needs a complete ingested document in Markdown, use
`GET /api/v1/documents/{documentId}/text` or create a browser-safe URL with
`POST /api/v1/documents/{documentId}/markdown-download-ticket`. The internal
`get_document_markdown` tool gives the Ask or Extraction model exact paged
ranges of that same canonical Markdown while enforcing the selected tenant,
silo, and optional project scope.

## Authentication

All client-callable `/api/v1` routes require an API key except:

```http
GET /api/v1/health
```

`GET /api/v1/runpod/download/{jobId}` and `POST /api/v1/runpod/results` are
not client-callable exceptions. They require the short-lived bearer credential
issued for one RunPod embedding attempt; normal `brk_` API keys are rejected.

Send the API key as a bearer token:

```http
Authorization: Bearer brk_your_api_key_here
```

Example:

```bash
curl -sS "$API_BASE/me" \
  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY"
```

API keys are created under Railway admin **Configuration → API functionality → API keys**. The key is generated by the backend and starts with `brk_`.

## API Key Scopes

Each API key may have one or more scopes.

| Scope                    | Allows                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------- |
| `silos:read`             | List and fetch silos, and read RAG ingestion/search settings.                                      |
| `silos:write`            | Create silos and update RAG ingestion/search settings.                                             |
| `documents:read`         | List documents, fetch document metadata/status/chunks/text/downloads, and run RAG search.          |
| `documents:ingest`       | Upload documents into a silo and queue ingestion.                                                  |
| `documents:delete`       | Delete a document and its related stored objects.                                                  |
| `documents:reprocess`    | Queue reprocessing for an existing document.                                                       |
| `documents:cancel`       | Cancel an active queued or running document ingestion/reprocess job.                               |
| `rag:ask`                | Ask questions against RAG content.                                                                 |
| `rag:extract`            | Execute/fetch standalone extractions and manage saved multi-step extraction Tasks/runs.            |
| `generated-files:read`   | List and download generated files.                                                                 |
| `generated-files:delete` | Delete generated files and their stored objects.                                                   |
| `api-usage:read`         | Read redacted API usage logs for the current key or tenant.                                        |
| `libraries:read`         | List/search libraries and read their projects, documents, status, and downloads.                   |
| `libraries:write`        | Create/edit libraries and projects, upload files, and change document membership.                  |
| `libraries:grant`        | Grant library projects to silos and bind their tools to Ask or Extraction.                         |
| `task-datasets:read`     | Inspect Task Dataset groups, definitions, coverage, sources, records, conflicts, and transactions. |
| `task-datasets:write`    | Revise Task Dataset metadata and logically clear definitions or complete groups.                   |

The `/api/v1/me` endpoint only requires a valid API key and returns the key identity and scopes.

Administrators assign the three library permissions under **Configuration →
API functionality → API keys → Reference library access**. Select the permissions
on an existing key and choose **Save library access**. An API username inherits
the scopes of its assigned API key, so an API user sees the Reference Libraries
interface only when that key includes `libraries:read`. The
`libraries:grant` scope is deliberately separate because it can expose a
library project's RAG tool to a silo's Ask or Extraction workflow.

## Request Conventions

### JSON Requests

Most POST endpoints use JSON:

```http
Content-Type: application/json
```

### Multipart Uploads

Document ingestion uses multipart form data and accepts either a binary file
part or a public HTTPS URL source:

```http
Content-Type: multipart/form-data
```

- `file`: a real binary multipart file part. A URL string in this legacy field
  is also accepted for Bubble compatibility.
- `fileUrl`: the preferred field when Bubble's File Uploader provides an HTTPS
  URL instead of raw bytes.

At least one source is required. Do not set the multipart boundary manually;
Bubble and normal HTTP clients generate it. Send `fileName` with URL uploads so
the parser receives the correct extension.

### UUIDs

Most object IDs are UUID strings:

```text
1fb52fc2-b5ce-4853-b9a6-294ab95429ca
```

### Timestamps

Timestamps are returned as ISO 8601 strings.

### Pagination

List endpoints accept:

| Query param | Default | Min |     Max |
| ----------- | ------: | --: | ------: |
| `page`      |     `1` | `1` | `10000` |
| `pageSize`  |    `20` | `1` |   `100` |

Paginated JSON responses include:

```json
{
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 48,
    "totalPages": 3
  }
}
```

### Idempotency

Endpoints that create or mutate persistent state require:

```http
Idempotency-Key: unique-client-generated-key
```

The key can be any stable string up to 160 characters. A UUID is a good choice.

If the same API key sends the same idempotency key with the same request shape, the API replays the saved JSON response. If the request shape differs, the API returns:

```json
{
  "error": {
    "code": "idempotency_key_conflict",
    "message": "This Idempotency-Key was already used for a different request shape.",
    "details": null
  },
  "requestId": "..."
}
```

For the streaming Ask endpoint, an idempotency replay does not start a second
model run. It returns a short `ask.replayed` NDJSON stream containing the
original `runId` and `statusUrl`. Use that URL to retrieve the durable state.

Replayed responses include the `Idempotency-Replayed: true` header. API usage
logs also record `requestMetadata.idempotencyReplayed: true`.

Use idempotency keys for retries after network failures or client timeouts.
Generate a new key for every new logical operation, even when the new request
has the same URL and JSON body as an earlier operation.

If a project was created, later deleted, and a client reuses the original
project-create idempotency key, the API returns `409` with:

```json
{
  "error": {
    "code": "idempotency_replay_resource_deleted",
    "message": "This Idempotency-Key belongs to a project that has since been deleted. Send a new unique Idempotency-Key to create another project."
  },
  "requestId": "..."
}
```

Multipart upload hashes are canonicalized from the logical form fields, file metadata, and file bytes. The multipart boundary and field ordering do not affect the hash, so Bubble can safely retry the same upload with the same idempotency key even when it regenerates the multipart body.

### Standard Error Format

JSON API errors use:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "Request body did not match the API contract.",
    "details": {}
  },
  "requestId": "..."
}
```

Common status codes:

| Status | Meaning                                                         |
| -----: | --------------------------------------------------------------- |
|  `400` | Invalid JSON, missing idempotency key, or request hash problem. |
|  `401` | Missing or invalid API key.                                     |
|  `403` | API key is valid but does not have the required scope.          |
|  `404` | Requested silo, document, file, or extraction was not found.    |
|  `409` | Duplicate resource or idempotency-key conflict.                 |
|  `422` | Request body or query/form fields are invalid.                  |
|  `500` | Server/database/storage failure.                                |
|  `503` | Required runtime configuration is missing.                      |

## Silo Projects

Projects are optional sub-scopes inside a silo. A silo contains the full document set; a project contains a subset of those documents. One document can belong to multiple projects without being uploaded or ingested more than once.

When `projectId` is omitted from search, Ask, Extraction, Task run, generated-file list, or document-list requests, the API uses the whole silo. When `projectId` is supplied, the API limits retrieval/listing to documents assigned to that project.

To add existing ingested files to a project without re-ingesting them:

1. List the whole silo with `GET /api/v1/silos/{siloId}/documents` and no `projectId`.
2. List the current project membership with `GET /api/v1/silos/{siloId}/projects/{projectId}/documents`.
3. Send the complete desired membership list to `PUT /api/v1/silos/{siloId}/projects/{projectId}/documents`.

## Documents

Documents are original files uploaded into a silo. A document becomes searchable after the worker processes it and its status becomes `ready`.

Document list, upload, detail, status, and reprocess responses include a `downloads` object on each document:

```json
{
  "downloads": {
    "original": {
      "method": "GET",
      "url": "/api/v1/documents/document-uuid/download",
      "ticketMethod": "POST",
      "ticketUrl": "/api/v1/documents/document-uuid/download-ticket"
    },
    "markdown": {
      "method": "GET",
      "url": "/api/v1/documents/document-uuid/text",
      "contentType": "text/markdown; charset=utf-8",
      "ticketMethod": "POST",
      "ticketUrl": "/api/v1/documents/document-uuid/markdown-download-ticket"
    }
  }
}
```

Use `downloads.original.url` to stream the exact uploaded source file through Railway. Use `downloads.markdown.url` to stream the text/Markdown version created during ingestion. Bubble browser workflows should call the corresponding `ticketUrl`, then open the returned short-lived URL without exposing the API key. If no stored source-assembly Markdown exists yet, the Markdown ticket endpoint builds and privately caches canonical Markdown from the stored pages/chunks. Excel downloads return the sheet-by-sheet Markdown table assembly. PDFs and DOCX files with embedded-image analysis enabled include image-analysis sections for eligible extracted images, including vision descriptions, transcribed visible text, table conversions, and chart/value estimates where possible.

### `POST /api/v1/silos/{siloId}/documents`

Scope: `documents:ingest`

Idempotency required.

Uploads a file, creates a document record, creates a source `document_files` row, queues an ingestion job, and sets the document status to `queued`.

Supported source uploads currently include PDF, DOCX, Excel workbooks, Markdown, plain text, CSV, PNG, and JPEG. PDF, DOCX, and Excel sources are first assembled into a canonical Markdown file before chunking and embedding. Excel sheets are emitted as Markdown table sections with row numbers and Excel column letters preserved. DOCX embedded PNG/JPEG images are extracted as document assets and, when DOCX vision analysis is enabled, inserted back into the Markdown as vision-generated image analysis blocks. Markdown, text, and CSV files use the same canonical Markdown -> chunk -> embed path without a separate model call.

Form fields:

| Field             | Type                           | Required    | Notes                                                                                                                                                                                                                                               |
| ----------------- | ------------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file`            | file or HTTPS URL string       | Conditional | Original source bytes. | `fileUrl`         | HTTPS URL string               | Conditional | Preferred Bubble integration field. Railway downloads the Bubble-hosted file after public-network and size validation. Send either `file` or `fileUrl`.                                                                                             |
| `fileName`        | string                         | No          | Overrides uploaded or remote file name. Send this for `fileUrl` uploads so the source extension is preserved.                                                                                                                                       |
| `title`           | string                         | No          | Defaults to file name.                                                                                                                                                                                                                              |
| `mimeType`        | string                         | No          | Defaults to uploaded file MIME type. If omitted or `application/octet-stream`, the API infers common source types from the file extension, including `.docx`, `.xlsx`, `.xls`, `.xlsm`, `.xlsb`, `.md`, `.txt`, `.csv`, `.pdf`, `.png`, and `.jpg`. |
| `processingDepth` | `fast` \| `standard` \| `deep` | No          | Defaults to `standard`.                                                                                                                                                                                                                             |
| `projectId`       | UUID                           | No          | Assigns the uploaded document to this project/subset after the single document record is created. ## Ingestion Webhooks

Document upload and reprocess can include webhook fields.

Upload form fields:

```text
webhookUrl

```

Reprocess JSON fields:

```json
{
  "webhookUrl": "https://example.com/bubble-rag/webhook",
  "webhookSecret": "replace-with-your-shared-secret"
}
```

Webhook event names:

```text
document.ingest.succeeded
document.ingest.failed
document.reprocess.succeeded
document.reprocess.failed
```

Webhook request headers:

| Header                           | Notes                                                                  |
| -------------------------------- | ---------------------------------------------------------------------- |
| `Content-Type: application/json` | JSON payload.                                                          |
| `x-bubble-rag-event`             | Event name.                                                            |
| `x-bubble-rag-delivery-id`       | Unique delivery UUID.                                                  |
| `x-bubble-rag-signature`         | Present only when `webhookSecret` is set. Format: `sha256=<hex-hmac>`. |

Signature calculation:

```text
hex_hmac_sha256(raw_request_body, webhookSecret)
```

Payload:

```json
{
  "event": "document.ingest.succeeded",
  "tenantId": "tenant-uuid",
  "documentId": "document-uuid",
  "jobId": "job-uuid",
  "jobType": "ingest",
  "status": "succeeded",
  "errorMessage": null,
  "occurredAt": "2026-07-19T00:05:00.000Z"
}
```

Webhook delivery attempts are recorded in the database table `api_webhook_deliveries`.

## Reference Libraries

Reference libraries are tenant-wide document collections outside every silo.
A library contains projects; each project groups documents and defines one
model-facing RAG tool. API usernames see the Libraries navigation only when
their associated key has `libraries:read`.

`libraries:grant` is intentionally separate and is never inferred from an
empty or legacy scope list. It changes which shared documents a silo can read.

Library document status, chunks, original files, Markdown, reprocessing,
embedding, cancellation, and physical deletion use the existing
`/api/v1/documents/{documentId}/...` endpoints. Those routes require
`libraries:read` for read operations and `libraries:write` for mutations
when the document has no silo. Silo document permissions do not grant access to
library documents.

`pageSize` pagination.

`description`, or both.

### `DELETE /api/v1/libraries/{libraryId}`

## Template Groups

A Template Group defines one dynamically named model tool. Assigning the group
to a silo makes that tool available to both Ask and Extraction. The model is
instructed not to use it unless the user's instructions request a template.
Specific template names use title search; general document purposes use the
stored description vectors with title fallback.

### `GET /api/v1/template-groups`

Scope: `templates:read`. Lists Template Groups and their stable IDs with
standard `page` and `pageSize` pagination.

### `GET /api/v1/template-groups/{templateGroupId}`

Scope: `templates:read`. Returns one tenant-owned Template Group.

### `PATCH /api/v1/template-groups/{templateGroupId}`

Scope: `templates:write`. Idempotency required. Accepts any combination of
`name`, `toolName`, `toolDescription`, and `enabled`.

### `GET /api/v1/template-groups/{templateGroupId}/templates`

Scope: `templates:read`. Lists the active, non-deleted templates in the group
with their stable IDs, latest ingestion status, latest job, asset count, review
suggestions, and delete URL. Each latest-version review suggestion reports its
stable ID, importance, category, saved Word page number when available, source
location, issue, and recommended source-DOCX edit. The response also reports
the number of findings ignored for the current ingestion.
Supports standard `page` and `pageSize` pagination plus an optional `query`
title filter.

Poll this endpoint while `latestJob.status` is `queued` or `running`.
`latestJob.stage` is the current ingestion step and `latestJob.lockedAt` is the
worker heartbeat; `queuedAt`, `startedAt`, `finishedAt`, `attempts`, and
`maxAttempts` provide the remaining activity context. A
`descriptionEmbeddingStatus` of `awaiting_ingestion` is expected during an
active run because the description vector is queued only after ingestion has
generated the detailed description.

An ingestion with no material warnings, unresolved items, or improvement
suggestions finishes as `completed`. A `needs_review` version includes one or
more actionable `latestVersion.reviewSuggestions`. Each suggestion may have
several alternatives. Only alternatives with `safeToImplement: true` have an
`implementUrl`. The latest version also reports its six `reviewPasses`, parent,
source kind, review cycle, convergence status, and pinned contract digest.

### `POST /api/v1/template-groups/{templateGroupId}/templates/{templateId}/versions/{versionId}/review-findings/{findingId}/ignore`

Scope: `templates:write`. Marks one open finding irrelevant for this immutable
version. If no open findings remain, the version becomes `completed`. This
does not edit the DOCX and therefore does not require idempotency.

### `POST /api/v1/template-groups/{templateGroupId}/templates/{templateId}/versions/{versionId}/review-findings/{findingId}/implement`

Scope: `templates:write`. Idempotency required. Resolves the stored alternative
server-side; callers cannot supply OOXML operations. The request must pin the
exact source and compiled contract:

```json
{
  "alternativeId": "set-scope-section",
  "expectedSourceSha256": "64-lowercase-hex-characters",
  "expectedContractDigest": "64-lowercase-hex-characters"
}
```

The server applies the validated edit to staged bytes, recompiles the DOCX,
stores version N+1 with a parent/provenance link, records the action, and queues
all six ingestion passes. It rejects stale versions, changed checksums/digests,
unvalidated alternatives, and corrections beyond the review-cycle limit.

### `DELETE /api/v1/template-groups/{templateGroupId}/templates/{templateId}`

Scope: `templates:write`. Idempotency required. Removes the template
immediately from catalog and model-tool searches, cancels queued ingestion and
embedding work, and frees its catalog name for a replacement upload. Immutable
source versions and job history remain privately retained for reproducibility.

### `GET /api/v1/template-groups/{templateGroupId}/silos`

Scope: `templates:grant`. Returns the complete `siloIds` assignment list.

### `PUT /api/v1/template-groups/{templateGroupId}/silos`

Scope: `templates:grant`. Idempotency required. Replaces the complete list;
omitted silo IDs lose access.

```json
{
  "siloIds": ["silo-uuid-1", "silo-uuid-2"]
}
```

### `DELETE /api/v1/template-groups/{templateGroupId}/silos/{siloId}`

Scope: `templates:grant`. Idempotency required. Removes one assignment.

### `GET /api/v1/federated-datasets`

Scope: `federated:read`. Lists Federated Datasets and their stable IDs with
standard `page` and `pageSize` pagination. Each entry reports the model tool
name, description, enabled state, entry count, and assigned silo count. This is
the call to make when you need a `datasetId` for the assignment routes.

### `POST /api/v1/federated-datasets`

Scope: `federated:write`. Idempotency required. Creates a dataset definition.
`toolName` is derived from `name` when omitted; it must be unique per tenant,
3-64 characters, and match `^[a-z][a-z0-9_]*$`.

```json
{
  "name": "Grant Registry",
  "toolName": "grant_registry",
  "toolDescription": "One funded grant or capital project. Look up before writing any grant name or ID."
}
```

The definition is shared across silos. Its data is not: assigning it to two
silos gives each silo its own entries and its own ID sequence.

### `PATCH /api/v1/federated-datasets/{datasetId}`

Scope: `federated:write`. Idempotency required. Accepts any combination of
`name`, `toolName`, `toolDescription`, `enabled`, `idPrefix`,
`displayIdStrategy`, `displayIdPrefix`, `modelCanWrite`, and `modelCanDelete`.

## Ask

### `POST /api/v1/silos/{siloId}/ask`

Scope: `rag:ask`

Idempotency required.

Asks a grounded question in the selected silo. The endpoint presents the
request and scoped tool descriptions to the configured Ask model first. The
model decides whether it needs silo evidence, then issues focused RAG or source
inspection calls before composing the answer or building the requested file.

The ordinary JSON endpoint and streaming endpoint use the same bounded Ask
agent loop. The request reaches the model before retrieval. Enabled tools may
be called serially or, when the provider and runtime support it, as independent
parallel calls.
Railway executes the tool in the selected silo/project scope, returns the tool
result to the model, and continues until the model produces a final answer or
reaches the Ask task's configured tool-request limit. The default is 64 and the
Configuration page accepts 1-250. `rag_search` and `rag_documents` share one
configurable 0-100 retrieval-query budget, defaulting to 8 for Ask. Every
distinct normalized query in either a compound `rag_search` call or a
`rag_documents` batch consumes one unit. The model never supplies a silo or
project ID. For non-DOCX, non-template requests, an unavailable provider may
fall back to a retrieval-only grounded preview.

`rag_documents` is a separate, read-only discovery tool for Ask and general
Extraction. It is not exposed to the staged template Phase 1 planner or Phase 2
workers. A call supplies exactly one of `query` or `queries`; `query` is one
non-empty string, while `queries` contains 1-12 non-empty strings or keyed
`{"key":"...","query":"..."}` entries. Railway binds tenant, silo, and
optional project scope from the authenticated run and rejects model-supplied
`tenantId`, `siloId`, `projectId`, `taskDatasetId`, `sourceBatchId`, or
`documentId`. Each query returns distinct documents with rank, score,
percentile, observation state, and bounded source anchors. Scores are ranking
evidence, not calibrated confidence, and `unobserved` does not establish that
evidence is absent. Use `rag_search`, not `rag_documents`, to retrieve passages
for an answer. The same strict argument contract is enforced for native calls
and JSON-envelope calls: overlong queries, out-of-range options, unknown
properties, and model-supplied scope are rejected rather than silently
truncated, clamped, or redirected.

The discovery response is fail-closed and bounded. Each backend first shortlists
at most 50 distinct documents per query before expanding per-document hits.
The scoped preflight allows at most 100,000 documents, 100,000 chunk rows and
100,000 vector rows, with a 32 MiB aggregate artifact/metadata envelope and a
256 KiB individual chunk ceiling. Oversized corpora fail with a capacity error
before retrieval; they are never reported as no-match. The internal query wire
is capped at 1 MiB and the Unicode-aware raw response at 2 MiB.
Keyword and vector modes use one backend operation per query; hybrid uses two. Capacity is derived as
150 signals per query, up to 1,800 for a 12-query batch, and inconsistent or
truncated accounting is rejected. A hybrid embedding failure falls back to
keyword for only the affected query and reports `vector_embedding_failed`; the
same failure in vector-only mode is an explicit failed result, never a
fabricated no-match. Model-facing hybrid ranking consistently applies 0.72
vector and 0.28 keyword weights even when a returned signal has only one
modality. If the final model-facing batch would exceed the 60,000-character
tool-result limit, Railway keeps valid JSON and every query summary, removes
anchor excerpts, and then fairly removes the lowest-ranked documents at one
common per-query depth. The response includes `outputTruncation` counts and
guidance to retry with fewer queries or a lower `topK`; it never returns a raw,
unparseable JSON prefix.

`get_document_markdown` is an internal model tool, not a public API endpoint.
The model supplies a document ID returned by `rag_documents`, `rag_search`, or
`list_files` and receives exact canonical Markdown. Larger files include
`nextOffset` and `complete`, allowing
lossless sequential retrieval without silently truncating the document.
Railway rejects documents outside the selected silo/project scope.

Every Ask model call receives a freshly generated UTC timestamp plus the Ask
task's configured reference location and IANA time zone. This includes each
follow-up tool-loop call, so relative dates and daylight-saving rules are
evaluated against the current request time. API callers do not send these fields.

Body:

| Field                        | Type                                       | Required | Notes                                                                                                                                                       |
| ---------------------------- | ------------------------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `question`                   | string                                     | Yes      | 1 character up to the configured Ask Model Task maximum; default 100,000 and absolute ceiling 1,000,000.                                                    |
| `topK`                       | integer                                    | No       | 1-50. Defaults to the configured Ask task Top K.                                                                                                            |
| `projectId`                  | UUID                                       | No       | Restricts Ask to a project/subset inside the silo.                                                                                                          |
| `documentId`                 | UUID                                       | No       | Restricts Ask to one ready document in the silo.                                                                                                            |
| `chunkTypes`                 | array                                      | No       | Optional list of chunk types to use.                                                                                                                        |

### `POST /api/v1/silos/{siloId}/ask/stream`

Scope: `rag:ask`

Idempotency required.

Starts the same Ask workflow as the ordinary endpoint but returns
`application/x-ndjson`. Every line is one complete JSON event. Do not parse the
whole response as one JSON document. Read a line, parse that line, update the
UI, and continue until the connection closes.

The request body is identical to `POST /api/v1/silos/{siloId}/ask`.

Request:

```bash
curl -N "$API_BASE/silos/$SILO_ID/ask/stream" \

  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/x-ndjson" \
  -H "Idempotency-Key: ask-stream-$(uuidgen)" \
  -d '{
    "question": "What is the renewal date and where is it stated?",
    "projectId": "project-uuid",
    "searchMode": "vector",
    "topK": 20
  }'
```

The response headers include:


When the model requests complete source context, streamed tool events identify
`get_document_markdown`. The full Markdown remains in the private model/tool
conversation; the event journal stores a bounded preview and completion
metadata rather than duplicating the entire document.

Provider-visible reasoning differs by provider:

- Ollama thinking-capable models stream their `message.thinking` content when
  supported by the selected model and configured effort.
- OpenAI uses Responses API reasoning-summary events. This is a provider
  summary, not private raw chain-of-thought. Models that do not support the
  reasoning-summary option are retried without it and continue streaming model
  output.
- Modular forwards provider-exposed reasoning deltas when the selected model
  includes them in its OpenAI-compatible streaming response.
- Tool events are produced by Railway from actual execution. They do not rely
  on the model narrating which tool it believes it used.

## Extractions

Standalone Extraction is synchronous. Railway performs scoped RAG retrieval,
runs the configured Extraction model/tool loop, writes the generated file, and
persists the extraction run and result before returning HTTP `200`. This call
can therefore remain open for the configured model timeout. Use a stable
idempotency key when retrying after a client timeout.

Saved multi-step Tasks use a different execution model: `POST
/api/v1/tasks/{taskId}/run` returns `202` and runs the extraction steps in the
background one by one. Use Task runs when the caller needs a durable queued
workflow containing one or more extraction steps.

Standalone extractions and sequential Task steps use the saved Extraction model
task policy. Railway presents the extraction request to the model before RAG.
The model can call scoped `rag_documents` to discover likely source documents
and `rag_search` to retrieve answer passages when evidence is needed. Both
tools share **Max RAG searches per request** (`0-100`, default `24`), and every
distinct normalized query consumes one unit. **Max tool requests** is a
separate overall ceiling (`1-250`, default `120`). **Max request characters**
applies to the Extraction request itself (`4,000-1,000,000`, default
`100,000`). Usage records the configured request limit and the actual shared
RAG query count.

## Tasks

Tasks are reusable extraction workflows. A saved Task is not tied to a silo. A Task may start with no extraction items while it is being drafted. A Task run is tied to one selected silo and executes the saved extraction items sequentially. Each step can either create a generated file or run as a cache-building step with `outputFileEnabled: false`. A cache-building step can research and stage Task Dataset records for later steps or future runs, is included in Task completion counts, and succeeds with `generatedFileId: null`. If a Task has no items, the run completes successfully without creating generated files.

Each extraction item uses the configured Extraction model task, including its configured RAG search mode and retrieval top K. File-producing steps use the existing generated-file path. Cache-building steps do not expose file-writing or document-finalization tools and return only a short completion summary for run history; their extraction run, evidence, telemetry, Task Dataset staging, and Task step status are still persisted. If a file-producing item specifies a file name that already exists in the target silo, the extraction tool overwrites it by deleting the existing generated file first.

`strictTaskDataset` is an optional per-step enforcement flag. It defaults to
`false`, preserving the normal model-directed Task Dataset behavior. When it is
`true`, the step cannot complete until the model successfully performs a
meaningful `task_dataset` operation, such as inventory, reuse/search, applying a
template suggestion, creating/recreating a definition, or staging records.
Catalog and describe-only calls do not satisfy the requirement. The value is
snapshotted into the Task run item, so editing the Task after a run starts does
not change that run. If the model still tries to finish without the required
dataset work after corrective reminders, the step fails and the shared Task
Dataset transaction is discarded rather than publishing a partial cache.

`inputData` is not added to any saved Task-step request. It is stored with the
immutable Task run configuration and appended at the very bottom of every
step's model context under **Input data**. Its factual values and parameters
take precedence for that run over conflicting request assumptions, retrieved
source values, previous generated output, or Task Dataset records. It remains
data and cannot override system, access, safety, or tool rules. Blank input is
ignored.

When `fileNameModifier` is present, the runner removes whitespace, control
characters, and the invalid filename characters `< > : " / \\ | ? *`, then
adds `-<modifier>` before the format extension. The output extension continues
to come from the Task step's output format. For example,
`town-manager-report.docx` plus `August: 2026 / Q3*` becomes
`town-manager-report-August2026Q3.docx`. Blank input or a value that becomes
empty after sanitization is ignored. Cache-building steps with file output
disabled do not use the modifier. The sanitized, modified name is also the name
used when resolving a previous generated reference.

When `use_previous_generated_reference` is `true`, the runner looks in the
selected silo for the newest generated file with the task item's output name
and format. If found, its complete content is read before overwrite and added
to that item's model context as the previous version of the output. The model
is instructed to:

- reuse an old identifier for a current entry only when current RAG sources
  support the same entity;
- never recycle an old identifier for a different entity or meaning;
- treat the old file as historical reference data rather than current source
  evidence; and
- omit entries no longer found in current sources unless the item request asks
  for historical/progress reporting, in which case the original identifier and
  entry may be retained with a `not found` status or the equivalent requested
  status.

If no matching output exists, the item runs normally without a previous
reference. Passing `false` or omitting the field preserves the existing
behavior.

Delivery request headers:

| Header                     | Present          | Value                                                               |
| -------------------------- | ---------------- | ------------------------------------------------------------------- |
| `content-type`             | Always           | `application/json`                                                  |
| `x-bubble-rag-event`       | Always           | Same lifecycle event name as the body `event` field.                |
| `x-bubble-rag-delivery-id` | Always           | Same UUID as the body `deliveryId` field.                           |
| `x-bubble-rag-signature`   | Signed runs only | `sha256=<hex-hmac>` computed over the exact raw UTF-8 request body. |

Verify a signed callback against the raw request body before parsing its JSON.
Delivery attempts are recorded, and a callback failure does not change the
Task-run result. An unsigned run omits `x-bubble-rag-signature`. The signing
secret is encrypted at rest and is never returned by Task-run APIs.

**Registering the webhook.** `webhookUrl` and `webhookSecret` are per run, not
per Task. They are supplied on `POST /api/v1/tasks/{taskId}/run` and stored on
that Task run only, so every run that needs callbacks must send them again.
Confirm registration from the `202` response fields `taskRun.webhookConfigured`
and `taskRun.webhookSigned`; `GET /api/v1/task-runs/{runId}` reports the same two
booleans. Neither the URL nor the secret is ever returned.

Validation applied when the run is created:

- `webhookUrl` is limited to 2048 characters and must use `http:` or `https:`.
  Anything else fails with `Webhook URL must use HTTP or HTTPS.`
- `webhookSecret` is limited to 500 characters and requires `webhookUrl`.
  Sending a secret alone fails with `A webhook URL is required when a signing
secret is set.`
- Signing requires `ADMIN_SESSION_SECRET` to be configured on the web service.
  Without it, a run that sets `webhookSecret`
  fails with `500 task_run_create_failed`. The secret is encrypted with
  AES-256-GCM before it is stored.

**Event sequence.** Every run with a webhook receives `task.run.started`, zero
or more `model.status.updated` events, and exactly one terminal event.

| Event                  | Sent when                                                     | `item`                        |
| ---------------------- | ------------------------------------------------------------- | ----------------------------- |
| `task.run.started`     | The run moves from `queued` to `running`.                     | `null`                        |
| `task.run.progress`    | An extraction item finishes successfully.                     | The completed item.           |
| `model.status.updated` | The active model publishes a user-visible progress update.    | The active item and request.  |
| `task.run.succeeded`   | All items completed. Empty Tasks emit this right after start. | `null`                        |
| `task.run.failed`      | An item or the run failed. The run stops here.                | The failing item, when known. |
| `task.run.cancelled`   | `POST /api/v1/task-runs/{runId}/cancel` was accepted.         | `null`                        |

A failed item produces `task.run.failed`, not a `task.run.progress` event.

**Delivery semantics.**

- **One attempt per event. There are no retries.** A timeout or non-2xx response
  is logged and the run continues unchanged.
- Each delivery times out after 10 seconds, then the request is aborted.
- Deliveries are sent inline and in order, and the run waits for each one, so a
  slow endpoint slows the whole Task run by up to 10 seconds per event. Return
  `200` immediately and do your processing asynchronously.
- Any non-2xx response is recorded as failed with
  `Webhook returned HTTP <status>.`
- Every attempt is written to `api_webhook_deliveries` against
  `extraction_task_run_id`, including `event_type`, `status`, `status_code`,
  `error_message`, the full `request_body`, and the first 2000 characters of your
  `response_body`. Do not echo anything sensitive in your response body.
- `deliveryId` is a fresh UUID per event. Use it, or `taskRunId` plus `event`
  plus `item.position`, to make your handler idempotent.

**Verifying the signature.** Compute HMAC-SHA256 over the exact raw request body
and compare against `x-bubble-rag-signature` in constant time. Parse the JSON
only after the comparison succeeds.

```js
import { createHmac, timingSafeEqual } from "node:crypto";

function isValidTaskWebhook(rawBody, signatureHeader, secret) {
  const expected = `sha256=${createHmac("sha256", secret).update(rawBody).digest("hex")}`;
  const a = Buffer.from(expected);
  const b = Buffer.from(signatureHeader ?? "");

  return a.length === b.length && timingSafeEqual(a, b);
}
```

**Reconciling.** Because there are no retries, treat callbacks as an
optimisation rather than a guarantee. If a terminal event has not arrived when
expected, poll `GET /api/v1/task-runs/{runId}` for the authoritative status and
per-item `generatedFileId` values.

## Typical Workflows

### Workflow 1: Create a Silo, Upload a Document, Wait Until Ready, Ask a Question

1. Create a silo:

```bash
curl -sS "$API_BASE/silos" \
  -X POST \
  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: create-silo-$(uuidgen)" \
  -d '{"name":"Client A"}'
```

2. Upload a document:

```bash
curl -sS "$API_BASE/silos/$SILO_ID/documents" \
  -X POST \
  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY" \
  -H "Idempotency-Key: upload-$(uuidgen)" \
  -F "file=@./source.pdf" \
  -F "processingDepth=standard"
```

3. Poll status:

```bash
curl -sS "$API_BASE/documents/$DOCUMENT_ID/status" \
  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY"
```

Wait until:

```json
{
  "document": {
    "status": "ready"
  }
}
```

4. Ask a question:

```bash
curl -sS "$API_BASE/silos/$SILO_ID/ask" \
  -X POST \
  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: ask-$(uuidgen)" \
  -d '{"question":"Summarize the document in three bullets.","topK":8}'
```

1. Search:

```bash
curl -sS "$API_BASE/silos/$SILO_ID/rag-search" \
  -X POST \
  -H "Authorization: Bearer $BUBBLE_RAG_API_KEY" \
  -H "Content-Type: application/json" \
```

```bash
curl -sS "$API_BASE/silos/$SILO_ID/ask" \
```

### Workflow 4: Upload With a Webhook Callback

```bash
curl -sS "$API_BASE/silos/$SILO_ID/documents" \
  -X POST \

  -H "Idempotency-Key: upload-webhook-$(uuidgen)" \
```

Your webhook receiver should:

1. Read the raw request body.
2. Compute `sha256=<hex_hmac_sha256(raw_body, webhookSecret)>`.
3. Compare it to `x-bubble-rag-signature` using constant-time comparison.
4. Use `event`, `documentId`, `jobId`, and `status` to update your external system.

## Bubble API Connector Notes

For Bubble:

- Store the API key in Bubble's private API Connector authentication settings, not in client-visible fields.
- Use `Authorization: Bearer YOUR_KEY` as a shared header.
- For JSON endpoints, set `Content-Type: application/json`.
- For file ingestion, configure a multipart/form-data call with a file parameter named `file`.
- Add an `Idempotency-Key` header on create/upload/delete/cancel/reprocess/ask/extraction calls. A Bubble-generated UUID or unique workflow ID is ideal.
- Define the streamed Ask call as response type **Stream** and use `/silos/[silo_id]/ask/stream`.
- Treat each received line as one JSON event. Map or parse `payload.delta` for live reasoning/model output and inspect `type` to distinguish tool and terminal events.
- Save `X-Ask-Run-Id` when Bubble exposes response headers. Also save `runId` from the first parsed stream event so status recovery does not depend on header access.
- On a client error or page navigation, call `GET /ask-runs/[run_id]` and poll until `askRun.terminal` is `yes`.
- Save returned IDs:
  - `silo.id`
  - `document.id`
  - `job.id`
  - `questionLog.id`
  - `askRun.id`
  - `generatedFile.id`
  - `extractionRun.id`
- For source citations, store both `sourceDocument.name` and `sourceDocument.id`.

### Idempotency Storage

Idempotent JSON responses are stored in `api_idempotency_keys`. Replayed responses are returned as JSON with the original saved status code. Streaming Ask stores the created run identity instead of the potentially large stream body. Replaying that request returns an `ask.replayed` event and never starts a duplicate model run.

## Task Dataset Read and Clear API

Task Dataset public read endpoints expose only committed definitions and active
records. Model-authored writes remain restricted to verified saved Task runs
through the server-owned tool context. A group is uniquely scoped
to tenant + saved Task + silo + explicit project-or-no-project. All steps in
that saved Task share the same group for that scope.

Record and source continuation tokens are signed, opaque, query-bound, expire
after 15 minutes, and are fenced to the group's active generation. Changing a
query requires starting without the old cursor. A clear advances generation,
so using a pre-clear cursor returns `task_dataset_cursor_stale` (`410`).

### `GET /api/v1/tasks/{taskId}/dataset-groups`

Scope: `task-datasets:read`. Lists groups for the saved Task. Optional
`siloId` and `projectId` filters distinguish project-specific groups from the
no-project whole-silo group. Use `projectId=` to select no-project explicitly.
Accepts `page` and `pageSize`.

### `GET /api/v1/tasks/{taskId}/dataset-groups/{groupId}`

Scope: `task-datasets:read`. Returns group counters, all active definition
descriptions and policies, the 20 most recent publication transactions, and
recent purge jobs. Internal purge cursors are never returned.

### `GET /api/v1/tasks/{taskId}/dataset-groups/{groupId}/datasets`

Scope: `task-datasets:read`. Lists active definitions and their committed
record, conflict, and source counts. Definition creation is intentionally not
available until Phase 3's staged write/claim tool.

### `DELETE /api/v1/tasks/{taskId}/dataset-groups/{groupId}/datasets`

Scope: `task-datasets:write`. Requires `Idempotency-Key` and body
`{"confirm":true}`. Immediately marks every definition in the group deleting,
invalidates open publication claims/transactions, advances the generation,
repairs visible counters, and enqueues bounded physical purge. The response
reports the purge job ID and hidden-row counts. A failed maintenance wake does
not reverse logical clear; the scheduler resumes the queued job.

### `GET /api/v1/tasks/{taskId}/dataset-groups/{groupId}/datasets/{datasetId}`

Scope: `task-datasets:read`. Describes one active definition and includes its
stable-document-ID coverage summary.

### `PATCH /api/v1/tasks/{taskId}/dataset-groups/{groupId}/datasets/{datasetId}`

Scope: `task-datasets:write`. Requires `Idempotency-Key`. Accepts `name` and/or
`description` plus the required positive `expectedRevision`. A concurrent
metadata revision returns `409`; reload the definition before retrying.

### `DELETE /api/v1/tasks/{taskId}/dataset-groups/{groupId}/datasets/{datasetId}`

Scope: `task-datasets:write`. Requires `Idempotency-Key` and body
`{"confirm":true}`. Clears every stored revision/data row belonging to the
definition key, advances group generation, and enqueues physical cleanup. The
next successful saved Task run is expected to recreate the framework.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/coverage`

Scope: `task-datasets:read`. Reports the scope level, active generation,
definition revision, per-state source counts, ready documents in scope,
covered/uncovered stable document IDs, and changed Markdown digests. Digest
changes are diagnostic only; re-ingesting the same document ID does not make
it uncovered.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/efficiency`

Scope: `task-datasets:read`. Returns the definition's advisory source-scope
revision, last commit-safe inventory checkpoint, refresh recommendation,
measured RAG exclusions/returns, document-level reuse percentage, classified
run totals, readiness, and at most 20 recent measured transactions. Optional
`windowDays` is bounded from 1 to 365 and defaults to 30. The response contains
no record payloads, source text, embeddings, or raw vectors.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/source-documents`

Scope: `task-datasets:read`. Document-summary alias for committed source
coverage. Accepts `query`, `state=committed|not_applicable`, `pageSize` up to
200, and an opaque `cursor`. Page numbers are deliberately absent.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/sources`

Scope: `task-datasets:read`. Returns the committed source snapshot fields,
including stable document ID, file/title, source document date, dataset-added
date, record/conflict counts, stored digests, current Markdown digest, and a
diagnostic changed-digest flag. Staged/claimed worker rows are not exposed.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/records`

Scope: `task-datasets:read`. Searches/lists active records. Parameters are:

- `mode`: `text` (default), `semantic`, or `hybrid`; semantic/hybrid require an
  enabled bounded semantic policy and non-empty query;
- `query`: bounded query text over configured searchable paths/semantic
  projection;
- `exactLogicalKey`: exact canonical identity;
- `conflictState`: `none`, `conflicted`, or `resolved`;
- `select`: comma-separated configured summary JSON pointers;
- `filters`: URL-encoded JSON array of `{path,op,value}` filters, limited to
  declared filterable paths;
- `sort`: `record_seq` or `record_seq_desc`;
- `pageSize`: 1-200; and
- `cursor`: signed continuation token returned by the preceding page.

List payloads are capped at 512 KiB. They return summaries/projections, not
unbounded provenance. Semantic/hybrid responses also report requested/actual
mode, index-pending status, the current embedding profile/readiness summary,
and semantic/text/hybrid scores when applicable. Exact filters are applied
before vector Top K. Raw vectors are never returned. Fetch one record for its
full payload and source detail.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/records/{recordId}`

Scope: `task-datasets:read`. Returns one active record and at most 100 active
source contributions, each with bounded evidence and its source snapshot. The
`provenanceTruncated` flag reports whether more contributions exist.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/conflicts`

Scope: `task-datasets:read`. Uses the same bounded search/projection/cursor
generation fence as record listing but returns a review-specific shape with the
logical key, record revision, dates, and up to 100 complete preserved variants.
The review is intentionally read-only; it never overwrites evidence.

### `POST /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/aggregate`

Scope: `task-datasets:read`. Accepts up to three `groupBy` JSON pointers, one to
eight measures (`count`, `sum`, `avg`, `min`, or `max` with a unique `as`), up
to twelve exact filters, optional `conflictState`, and a group limit up to 500.
Group and numeric measure paths must be declared in `aggregatePaths`; filters
must also be declared filterable. Exact filters run before grouping. Responses
are capped at 512 KiB and report total/matched/returned groups and truncation.

### `GET /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/exports`

Scope: `task-datasets:read`. Lists recent snapshot export jobs, their immutable
generation/watermark, status, counts, bounded error, and completed
`generatedFileId` used by the normal generated-file download endpoint.

### `POST /api/v1/task-dataset-groups/{groupId}/datasets/{datasetId}/exports`

Scope: `task-datasets:read`. Requires `Idempotency-Key` and queues an immutable
snapshot export. The body accepts `format` (`jsonl` or `csv`), up to
40 selected summary paths, up to twelve exact filters, optional conflict state,
and an optional file name. CSV requires selected columns. The worker holds the
active generation and record-sequence watermark captured at request time,
renews its lease while paging, stops at 50 MiB, and publishes a generated file
only after the whole export succeeds.

### `GET /api/v1/task-dataset-operations`

Scope: `task-datasets:read`. Optional `groupId` narrows usage and hot-path rows.
The response includes effective quotas, quota pressure, expression-index jobs,
and export/purge/deletion queues. Installation-wide relation and autovacuum
statistics plus the measured partition recommendation remain in the internal
operator explorer because they can summarize activity across tenants. Raw
embedding vectors are never included.

### `GET /api/v1/task-dataset-groups/{groupId}/transactions`

Scope: `task-datasets:read`. Pages through atomic Task-run publication logs,
including generations, counts, manifest digest, terminal state, and bounded
failure summary. Accepts `page` and `pageSize` up to 100.

### Security

- API keys grant tenant-wide access according to their scopes.
- Silo-level API key restrictions are not implemented yet.
- Keep API keys in server-side or private integration configuration.
- Do not expose API keys in browser JavaScript, Bubble client workflows, public logs, screenshots, or generated files.
- Rotate/delete API keys under Railway admin **Configuration → API functionality → API keys** when no longer needed.

### Sleep/Wake Behavior

The Railway web service is configured with `sleepApplication: true`. A sleeping service may take a short moment to wake on the next request.

### Current Limitations

- RAG search supports keyword, vector, and hybrid modes. Vector/hybrid ranking requires `document_embeddings` rows for the active embedding version; otherwise requests fall back to keyword retrieval and report the embedding error in usage/scoring metadata.
- Ask and Extraction use separately saved configurations over one shared scoped tool runtime. Each supports a configurable 1-250 model-requested tool rounds, defaulting to 64, plus an independent 0-100 RAG-search ceiling, defaulting to 8, and receives current UTC/reference-time-zone context on every provider call.
- Ollama thinking output depends on the selected model. OpenAI reasoning-summary output depends on Responses API model support. Modular reasoning output depends on the selected model's OpenAI-compatible stream. Tool and status events remain available even when a model does not expose reasoning information.
- Saved Task runs currently execute sequential extraction steps from the Railway web service background runner. If very large chained Tasks become common, this can move to a dedicated worker queue using the same task-run tables.
- API keys are scoped by capability, not by individual silo.
- The public API does not currently expose API-key management endpoints;
  manage keys under Railway admin **Configuration → API functionality → API keys**.

## Minimal Client Example

Node.js example:

```js
const API_BASE = "https://web-production-3bf65.up.railway.app/api/v1";
const API_KEY = process.env.BUBBLE_RAG_API_KEY;

async function api(path, options = {}) {
  const response = await fetch(`${API_BASE}${path}`, {
    ...options,
    headers: {
      authorization: `Bearer ${API_KEY}`,
      ...(options.body instanceof FormData
        ? {}
        : { "content-type": "application/json" }),
      ...(options.headers ?? {}),
    },
  });

  if (!response.ok) {
    const error = await response.json().catch(() => null);
    throw new Error(error?.error?.message ?? `HTTP ${response.status}`);
  }

  const contentType = response.headers.get("content-type") ?? "";
  return contentType.includes("application/json")
    ? response.json()
    : response.arrayBuffer();
}

const { silos } = await api("/silos");
const siloId = silos[0].id;

const answer = await api(`/silos/${siloId}/ask`, {
  method: "POST",
  headers: {
    "idempotency-key": crypto.randomUUID(),
  },
  body: JSON.stringify({
    question: "What are the main topics in this silo?",
    topK: 8,
  }),
});

console.log(answer.answer);
console.log(answer.sources.map((source) => source.sourceDocument));
```

Streaming Ask example:

```js
async function streamAsk(siloId, question) {
  const response = await fetch(`${API_BASE}/silos/${siloId}/ask/stream`, {
    method: "POST",
    headers: {
      authorization: `Bearer ${API_KEY}`,
      "content-type": "application/json",
      "idempotency-key": crypto.randomUUID(),
    },
    body: JSON.stringify({ question, searchMode: "vector", topK: 20 }),
  });

  if (!response.ok || !response.body) {
    throw new Error(`Streaming Ask failed with HTTP ${response.status}`);
  }

  const runId = response.headers.get("x-ask-run-id");
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";

  while (true) {
    const { done, value } = await reader.read();
    buffer += decoder.decode(value, { stream: !done });
    const lines = buffer.split(/\r?\n/);
    buffer = lines.pop() ?? "";

    for (const line of lines) {
      if (!line.trim()) continue;
      const event = JSON.parse(line);
      console.log(event.type, event.payload);

      if (event.type === "ask.completed") {
        return event.payload.result;
      }
    }

    if (done) break;
  }

  if (runId) {
    return api(`/ask-runs/${runId}`);
  }

  throw new Error("Ask stream closed before a terminal event.");
}
```
