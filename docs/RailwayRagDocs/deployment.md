# Deployment Notes

## Railway services

Deploy eight services from this monorepo:

| Service                 | Config                                | Public | Persistent volume          |
| ----------------------- | ------------------------------------- | ------ | -------------------------- |
| `web`                   | `/railway.web.json`                   | Yes    | None                       |
| `worker`                | `/railway.worker-cron.json`           | No     | None                       |
| `embeddings`            | `/railway.embedding.json`             | No     | `/root/.ollama`            |
| `maintenance`           | `/railway.maintenance.json`           | No     | None                       |
| `maintenance-scheduler` | `/railway.maintenance-scheduler.json` | No     | None                       |
| `settings`              | `/railway.settings.json`              | No     | `/data`                    |
| `postgrest`             | `/railway.postgrest.json`             | No     | None                       |
| `postgres-sql`          | `/railway.postgres.json`              | No     | `/var/lib/postgresql/data` |

The settings volume contains the encrypted SQLite database. Railway Serverless
sleep is enabled. A real settings request from web wakes the private service;
web then sends health pings for one minute after the most recent settings
access. When that activity lease ends, the pings stop and Railway's normal
ten-minute inactivity window can put the service back to sleep. The timer is
unreferenced and exists only in the `web` service, so workers and local tools do
not create a permanent keep-awake loop.

## Bootstrap-variable boundary

The only operator/bootstrap variables are:

- `ADMIN_AUTH_ENABLED`: only an explicit `true` allows new browser login
  sessions. Set it to `false` to lock new logins; protected routes, existing
  sessions, and API-key authentication keep their normal authorization rules.
- `ADMIN_SETUP_ENABLED`: only an explicit `true` permits setup/recovery token
  validation. Set it to `false` after setup; doing so immediately invalidates
  outstanding setup sessions.
- `ADMIN_SESSION_SECRET`: generated once, at least 32 random characters. It
  signs login sessions, derives domain-separated private-service credentials,
  and derives the settings database encryption key.
- `ADMIN_SETUP_TOKEN`: generated one-time administrator bootstrap/recovery
  token. Rotate it deliberately when access must be recovered.
- `SETTINGS_SERVICE_URL`: private locator, normally
  `http://${{settings.RAILWAY_PRIVATE_DOMAIN}}:8082`.
- `RAILWAY_POSTGRES_PASSWORD`: generated by the template rather than entered
  by the operator. PostgreSQL and Maintenance receive references to the one
  canonical secret; Maintenance encrypts the resulting owner connection in
  Settings during first-start reconciliation.
- `POSTGREST_AUTHENTICATOR_PASSWORD`: generated once and supplied only to the
  private PostgREST supervisor for its fixed PostgreSQL login.
- `POSTGREST_JWT_SECRET`: generated once and supplied only to PostgREST and
  Maintenance. Maintenance stores a signed service token in Settings, never
  this signing root.
- `RAILWAY_POSTGREST_BASE_URL`: fixed private service reference used by
  Maintenance for readiness verification and candidate registration.

Railway-provided identity values and fixed ports are platform topology, not
application configuration. No Supabase, model-provider, API-key, backup, or
runtime-tuning value belongs in Railway variables. The two Boolean access gates
must remain shared Railway variables rather than settings-vault records so an
operator can unlock access even when the vault is unavailable.

## First installation

1. Deploy the eight services and attach all three volumes.
2. Maintenance automatically provisions the blank local PostgreSQL candidate,
   applies the checked-in provider-neutral migrations, reloads local PostgREST,
   and registers it only after database identity and schema verification.
3. Leave both admin switches at their template default of `true`, open `/setup`,
   and enter `ADMIN_SETUP_TOKEN`.
4. Enter the Supabase project URL and service-role key used only for document
   object storage. Setup verifies Storage and activates local PostgreSQL plus
   local PostgREST; no Supabase database connection is required.
5. Create the first administrator.
6. Save provider access and model selections explicitly. A fresh vault contains
   layout metadata only and has no model settings.
7. Set `ADMIN_SETUP_ENABLED=false` after setup. Set
   `ADMIN_AUTH_ENABLED=false` too when browser login should be locked and API
   keys are the only intended entry point.

Railway PostgreSQL is the default relational data plane for documents, job
queues, runs, and pgvector. Supabase Storage remains the default independent
document-object provider. Provider access-point lease/rate-limit rows are a
disposable operational projection refreshed from the local vault by the worker.

## Existing installations

After saving the old Supabase connection, open Backups and select **Import
legacy Supabase settings**. The explicit import copies administrators,
application users, API-key records, runtime/RAG/model/task/context settings,
provider access points, provider-key pools, storage/RunPod settings, and
Supabase Vault provider secrets into the encrypted local vault. Source rows are
left intact for recovery; application code no longer treats them as settings.

## Settings backup and restore

From Backups, enter a password of at least 12 characters and export a
`.brsettings` file. The archive uses password-derived encryption independently
of the live installation key, so it can be restored into another installation.
Restore replaces the complete local settings state, including users and API
keys. Settings backups are manual only; no scheduler job is created.

Keep the backup file and its password separately. A backup without its password
is intentionally unrecoverable.

The manual `.brsettings` export contains the retained Railway connection when
one exists, including usable token or OAuth refresh material. The complete file
is password-encrypted; it must be handled as a credential backup. Scheduled
data-plane backups do not copy that Railway connection out of the Settings
Vault.

Export and verify a portable backup before rotating `ADMIN_SESSION_SECRET`.
That value derives the live database key, so existing SQLite records are not
readable under a replacement secret; restore the portable backup to re-encrypt
them under the new installation root.

Railway also generates `BACKUP_ENCRYPTION_KEY` for Maintenance. It encrypts
scheduled data-plane backups and every database-transfer archive. Retain it
with the installation's recovery material; losing it makes those S3 archives
intentionally unrecoverable. Maintenance refuses to create an unencrypted
off-platform backup or transfer when the key is absent. A manually supplied
backup key still overrides the generated key for that one archive.

Database transfer is separate from Settings restore. It requires a successful
S3 write/read/delete probe, an immutable target analysis and approval, verified
source and (when populated) target safety archives, maintenance downtime, and
post-restore verification before Settings changes the active route. See
[PostgreSQL/PostgREST portability Phase 5](setup/railway-postgres-postgrest-portability-phase-5.md).

## GitHub and Supabase migrations

The `supabase/migrations/*.sql` directory remains the schema source of truth.
Repository release workflows may still use GitHub-held Supabase deployment
credentials; those CI credentials are separate from Railway runtime
configuration and are never copied into the settings vault automatically.
